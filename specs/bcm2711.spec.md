# Broadcom BCM2711: the Raspberry Pi Arm stub (permissive overlay)

Adds to the `bcm2711` spec in `hardware-specs-docs` the facts that only the source of the
Raspberry Pi Arm stub, `armstubs/armstub8.S` in raspberrypi/tools, states. Each `[src]` bullet
says what that source does when built for BCM2711 (with `BCM2711` and `GIC` defined and
`HIGH_PERI` not defined), citing the lines through the `rpi-tools` entry above. No document says
the firmware's built-in stub is that build; the first bullet argues it, and every hardware
consequence below rests on it.

## Quick-facts

- **Which build ships.** For a 64-bit boot on the boards the `enable_gic` page names (it says
  Raspberry Pi 4B; this spec takes its wording to cover every BCM2711 board), the stub the firmware
  runs by default in Low Peripheral mode is most likely `armstub8.S` built with `BCM2711` and
  `GIC` defined; this is a candidate build, held with limited confidence, not an identified
  shipped revision.
  `[inference]` (premises: the default stub is built into the firmware and chosen by model and
  settings `[doc]` (Raspberry Pi documentation, config.txt boot options, `armstub`); `arm_64bit`
  defaults to 1 on Raspberry Pi 4, 400 and Compute Module 4 and 4S `[doc]` (config.txt boot
  options, `arm_64bit`), so the default stub is an AArch64 one; the GIC-400 is the default
  interrupt controller `[doc]` (legacy config.txt boot options, `enable_gic`); the stub the
  firmware supplies lacks high-peripheral support `[doc]` (legacy config.txt boot options,
  `arm_peri_high`); in `armstubs/` at the pin, `armstub8.S` is the only AArch64 source, as
  `armstub7.S` is the 32-bit stub; assumed, and tested by the TODO: the firmware's built-in
  64-bit stubs are built from `armstubs/armstub8.S`, which no document states; the firmware
  writes the magic and load-address words into a stub `[doc]` (Trusted Firmware-A
  documentation, Raspberry Pi 4 platform, "TF-A port design"), which this source carries, with
  release slots its comment ties to the firmware, per the anchors in the bullets below;
  its non-`HIGH_PERI` ARM Local and GIC addresses are the datasheet's Low Peripheral ones
  `[databook]` (BCM2711 ARM Peripherals, §6.5.1–6.5.2, p. 92);
  derivation: `BCM2711`, `GIC` and `HIGH_PERI` are the only conditionals in `armstub8.S`, so if
  the assumption holds the default is the `BCM2711` and `GIC` build) `TODO (verify on
  hardware)`: on a recorded board, configuration and firmware release, capture the whole stub
  image the firmware loads (through `setup_gic` past `0x100` and the trailing literals), and
  compare it with this build, excluding the words the firmware patches at `0xF0`–`0xFF`; or
  boot this build with `armstub=` and scope observations to it.
- **Generic timer frequency.** The BCM2711 build writes 54000000 (54 MHz) to `CNTFRQ_EL0` and 0
  to `CNTVOFF_EL2`. `[src]` ([src:rpi-tools: armstubs/armstub8.S:53-57 (OSC_FREQ)];
  [src:rpi-tools: armstubs/armstub8.S:110-112 (OSC_FREQ)];
  [src:rpi-tools: armstubs/armstub8.S:114-115 (CNTVOFF_EL2)])
- **SCR_EL3 bits.** The stub's `SCR_EL3` value sets RW (bit 10), HCE (bit 8), SMD (bit 7), bits
  5 and 4, and NS (bit 0), and writes it to `SCR_EL3`. By the architecture's field definitions,
  EL2 then runs in AArch64 and non-secure, HVC is enabled, and SMC is undefined at EL2; at EL1 it
  is undefined unless EL2 traps it first through `HCR_EL2.TSC`, which takes priority. `[src]`
  ([src:rpi-tools: armstubs/armstub8.S:59-66 (SCR_VAL)];
  [src:rpi-tools: armstubs/armstub8.S:121-123 (SCR_VAL)]), `[standard]` (Arm ARM DDI 0487 M.d,
  §D24.2.168 `SCR_EL3`: RW p. D24-9638, HCE and SMD pp. D24-9639–D24-9640, NS p. D24-9641)
- **SCR_EL3 value.** The value the stub writes is `0x5B1`. `[inference]` (premises: the six bits
  the previous bullet's anchors show, which the source names by bit position and never
  sums; derivation: 0x400 + 0x100 + 0x80 + 0x20 + 0x10 + 0x1 = 0x5B1) `TODO (verify on hardware)`:
  the register is EL3-only, so read it with a debugger that can access EL3 state.
- **Entry exception level and state.** The stub drops from EL3 to EL2 using SP_EL2 with D, A, I
  and F masked, after writing `0x30C50830` to `SCTLR_EL2` (its comment: the set bits are RES1;
  little-endian, MMU, caches and alignment checks off). The primary core then branches to the
  address in `kernel_entry32` with `x0` = the word at `dtb_ptr32` and `x1`–`x3` = 0, the register
  state the arm64 boot protocol asks for. `[src]`
  ([src:rpi-tools: armstubs/armstub8.S:74-80 (SPSR_EL3_VAL)];
  [src:rpi-tools: armstubs/armstub8.S:136-141 (SCTLR_EL2)];
  [src:rpi-tools: armstubs/armstub8.S:143-148 (SPSR_EL3_VAL)];
  [src:rpi-tools: armstubs/armstub8.S:163-171 (primary_cpu)]), `[standard]` (Linux arm64 boot
  protocol, booting.rst, "Call the kernel image")
- **SMPEN at EL3.** Before dropping to EL2 the stub writes `CPUECTLR_EL1` with only bit 6, SMPEN,
  set. `[src]` ([src:rpi-tools: armstubs/armstub8.S:71-72 (CPUECTLR_EL1_SMPEN)];
  [src:rpi-tools: armstubs/armstub8.S:129-131 (CPUECTLR_EL1_SMPEN)])
- **Patch words.** The stub image holds the magic word `0x5AFE570B` at offset `0xF0`, a version
  word at `0xF4`, a 32-bit device-tree pointer at `0xF8` and a 32-bit kernel entry address at
  `0xFC`; the last two are zero in the image and only read by the stub, and a comment says the
  firmware clears the eight bytes at `0xF0` after reading them so the slot serves as core 3's
  release word. The firmware writes the kernel and device-tree load addresses into a stub that
  carries a magic value. `[src]` ([src:rpi-tools: armstubs/armstub8.S:187-192 (spin_cpu3)];
  [src:rpi-tools: armstubs/armstub8.S:193-208 (stub_magic)];
  [src:rpi-tools: armstubs/armstub8.S:163-165 (primary_cpu)]), `[doc]` (Trusted Firmware-A
  documentation, Raspberry Pi 4 platform, "TF-A port design")
- **Secondary-core release: spin-table.** Cores whose `MPIDR_EL1` bits 1:0 are non-zero wait with
  `wfe`, each polling a 64-bit slot indexed by those bits: `0xD8` (core 0's slot, unused),
  `0xE0`, `0xE8`, `0xF0`. A non-zero value is the address they branch to, with `x0`–`x3` = 0.
  The stub is loaded at DRAM address 0, so the slot offsets are physical addresses. `[src]`
  ([src:rpi-tools: armstubs/armstub8.S:151-153 (MPIDR_EL1)];
  [src:rpi-tools: armstubs/armstub8.S:155-161 (spin_cpu0)];
  [src:rpi-tools: armstubs/armstub8.S:167-171 (boot_kernel)];
  [src:rpi-tools: armstubs/armstub8.S:175-189 (spin_cpu0)]), `[doc]` (Trusted Firmware-A
  documentation, Raspberry Pi 4 platform, "TF-A port design")
- **GIC programming at EL3.** In the `GIC` build every core, at EL3, writes `0x1E7` to its
  CPU-interface control register and `0xFF` to its priority mask, and writes all-ones to eight
  `GICD_IGROUPR` words (interrupt IDs 0–255); cores whose `MPIDR_EL1` bits 1:0 are non-zero also
  write 3 to the distributor control register, while core 0 branches past that write under a
  comment calling it the primary core. The stub's `GIC_DISTB` is `0xFF84_1000` and its `GIC_CPUB`
  `0xFF84_2000`. `[src]` ([src:rpi-tools: armstubs/armstub8.S:45-51 (GIC_DISTB)];
  [src:rpi-tools: armstubs/armstub8.S:85-89 (IT_NR)];
  [src:rpi-tools: armstubs/armstub8.S:133-135 (setup_gic)];
  [src:rpi-tools: armstubs/armstub8.S:214-235 (setup_gic)])
- **Interrupt groups at entry.** With the stub's GIC setup, every implemented interrupt is in
  Group 1 (non-secure): IDs 0–223 are the implemented range (less the unused PPIs 16–24, which
  the GIC-400 does not implement), so only seven group registers exist, and the stub's eighth
  word, `GICD_IGROUPR7`, lies beyond them. `[inference]` (premises: the stub writes all-ones to
  eight group words
  [src:rpi-tools: armstubs/armstub8.S:228-234 (setup_gic)]; NUM_SPIS=192 `[databook]` (BCM2711
  ARM Peripherals, §6.5.1, p. 92); ITLinesNumber is NUM_SPIS/32 and every ID up to
  (ITLinesNumber+1)×32−1 is implemented except 16–24 `[databook]` (GIC-400 TRM, §3.3, Table 3-2
  note d, p. 3-5); there are ITLinesNumber+1 group registers, and a bit for an unimplemented
  interrupt is RAZ/WI, and `GICD_IGROUPR0` (IDs 0–31) is banked per processor `[standard]`
  (IHI 0048B, §4.3.4, p. 4-89); every core runs `setup_gic` before its `eret`
  [src:rpi-tools: armstubs/armstub8.S:133-135 (setup_gic)], assuming the firmware starts all
  four cores at the stub's entry; Group 1 is the Non-secure group on the GIC-400 `[databook]`
  (GIC-400 TRM, §1.1, p. 1-2); derivation: ITLinesNumber is 6, so 7 registers cover IDs 0–223;
  each core's own write sets its banked copy for IDs 0–31, and the shared registers cover the
  SPIs; and the build-identity step in the first bullet) `TODO (verify on hardware)`: the group registers
  are secure-only, so read them back at EL3 from a modified stub or with a debugger that makes
  secure accesses.

## Gotchas

- **No EL3 runtime with the stock stub.** The stock stub sets `SCR_EL3.SMD`, which makes SMC
  undefined at EL2, and at EL1 unless EL2 traps it through `HCR_EL2.TSC`, so no SMC reaches EL3, and leaves EL3 for good through one `eret` without setting an EL3
  vector base, so there is no secure monitor to call: no SMC-based PSCI, and secondary cores come
  up only through the spin-table. For PSCI, load Trusted Firmware-A's BL31 with `armstub=`.
  `[inference]` (premises: `SCR_VAL` sets SMD and leaves EA, FIQ and IRQ, bits 3 to 1, clear
  [src:rpi-tools: armstubs/armstub8.S:59-66 (SCR_VAL)]; SMD set makes SMC undefined at EL1 and
  above, with an `HCR_EL2.TSC` trap to EL2 taking priority, and EA, FIQ and IRQ clear mean external aborts, SErrors, FIQs and IRQs below EL3 are not
  taken to EL3 `[standard]` (Arm ARM DDI 0487 M.d, §D24.2.168, pp. D24-9639–D24-9641); the
  stub's EL3 code ends in its only `eret` and never writes `VBAR_EL3`
  [src:rpi-tools: armstubs/armstub8.S:91-148 (_start)]; secondary cores leave the stub only when
  their slot turns non-zero
  [src:rpi-tools: armstubs/armstub8.S:151-161 (spin_cpu0)]; arm64 Linux brings secondaries up
  by spin-table or by PSCI `[standard]` (Linux arm64 boot protocol, booting.rst, CPU enable
  methods); BL31 provides PSCI on this platform `[doc]` (Trusted Firmware-A documentation,
  Raspberry Pi 4 platform); derivation: with SMC undefined and no exception routed to EL3, EL3
  is never entered again after the `eret`; with no EL3 code left to answer, there is no
  SMC-based PSCI; so of the two enable methods only spin-table remains, and the stub's slot poll
  is its only release path; all of this given the build-identity step in the first bullet) `TODO (verify on
  hardware)`: an SMC from EL2 should take an undefined-instruction exception at EL2.
- **What the stub set in the GIC is secure state.** A non-secure kernel cannot read back the
  stub's group settings: the group registers read as zero to non-secure accesses. Checking them
  needs a secure access at EL3 or from a debugger. `[standard]` (IHI 0048B, §4.3.4, p. 4-89),
  `[databook]` (GIC-400 TRM, §1.1, p. 1-2: the GIC-400 implements the GIC Security Extensions)
- **High peripheral mode needs another build.** With `HIGH_PERI` defined the source uses the
  full-map bases `0x4_C000_0000` (ARM Local) and `0x4_C004_1000` (distributor); a stub built for
  one peripheral mode programs the wrong addresses in the other, and the firmware's own stub
  does not support high peripheral mode. `[src]`
  ([src:rpi-tools: armstubs/armstub8.S:32-51 (HIGH_PERI)]), `[databook]` (BCM2711 ARM
  Peripherals, §6.5.1–6.5.2, p. 92: the GIC-400 and ARM_LOCAL bases differ between the full map
  and Low Peripheral mode), `[doc]` (Raspberry Pi documentation, legacy config.txt boot options,
  `arm_peri_high`)
